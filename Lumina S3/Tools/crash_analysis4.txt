# Crash Analysis Report - Lumina LED Controller
## Crash ID: 4 (coredump4.txt)
## Date: 2026-04-18

---

### 1. SUMMARY
- **Crash Type:** Task Watchdog Timer (TWDT) Timeout / Abort
- **Core:** 0
- **Crashed Task:** `CloudTask` (TCB: 0x3fcb8874)
- **Watchdog Timeout:** 30 Seconds
- **Primary Cause:** Core 0 CPU Starvation and Socket Mutex Contention.

---

### 2. DETAILED ANALYSIS

#### A. Watchdog Trigger
Like Crash 3, the system panicked because the IDLE task on Core 0 was starved for more than 30 seconds. This is a classic symptom of Core 0 being overwhelmed by network-related tasks and high-priority processing.

#### B. Socket Mutex Contention
In this specific coredump, `CloudTask` was blocked at `#9 0x420ad3d1 in sys_mutex_lock (pxMutex=0x3fca2684 <sockets+44>)`. 
- `CloudTask` was attempting a Firebase RTDB `setJSON` operation, which requires a socket.
- To perform socket operations, lwIP requires locking the global `sockets` mutex.
- The fact that `CloudTask` (Priority 1) stayed blocked long enough to trigger a 30-second watchdog suggests that whatever task held that mutex was either very slow or also starved.

#### C. Core 0 Traffic Jam
The task distribution remains the primary culprit:
- **`wifi` (Priority 23):** High priority, runs on Core 0.
- **`Stream_2` (Priority 3):** Firebase Stream listener, runs on Core 0.
- **`IOTask` (Priority 1):** MQTT and Smart Home, runs on Core 0.
- **`CloudTask` (Priority 1):** Firebase Telemetry, runs on Core 0.
- **`SystemTask` (Priority 0):** Sensors and Automation, runs on Core 0.

When `Stream_2` or `IOTask` are performing heavy network operations (like processing a large MQTT discovery payload or a Firebase stream update), they can hog Core 0. If they also hold the `sockets` mutex during these operations, they block `CloudTask`.

#### D. The I2C Factor
Simultaneously, `SystemTask` was at `#0 0x4037e5d2 in vPortEnterCritical` during an I2C read. While I2C itself doesn't cause a watchdog timeout, the fact that a Priority 0 task was mid-execution confirms that the higher-priority tasks were yielding *occasionally*, but not enough for the IDLE task to reset the timer.

---

### 3. RECURRING FINDINGS (Pattern Recognition)
Comparing Crash 3 and Crash 4 reveals a persistent architectural weakness:
1. **Core 0 is over-saturated.** Network processing, Firebase Streams, Firebase RTDB uploads, and MQTT processing are all competing for the same silicon.
2. **Blocking Network Logic.** The use of `delay()` in MQTT discovery and the intensive BearSSL handshakes in `CloudTask` create windows of time where the scheduler cannot effectively reach the IDLE task.
3. **Redundant Sensor Polling.** Multiple tasks are hitting the I2C bus independently, increasing the likelihood of a task being blocked while holding a mutex or waiting for hardware.

---

### 4. RECOMMENDATIONS

#### ✅ High Priority: Distribute the Load
1. **Move `CloudTask` to Core 1:** 
   `xTaskCreatePinnedToCore(cloudTask, "CloudTask", 12288, NULL, 1, &cloudTaskHandle, 1);`
   Moving the telemetry upload to the secondary core will immediately free up Core 0 for WiFi and MQTT management.
2. **Move `IOTask` to Core 1:** 
   Consider moving MQTT handling to Core 1 as well. Core 0 should be reserved for the WiFi driver, TCP/IP stack (lwIP), and system-level events.

#### ✅ Medium Priority: Modernize Task Logic
1. **Event-Driven Telemetry:** Instead of a fixed 2-second loop in `CloudTask`, consider using a timer or a notification from `SystemTask` to trigger an upload.
2. **Priority Re-alignment:** 
   - WiFi/TCPIP: 23 (System)
   - Stream Task: 3
   - LED Task: 2 (Core 1)
   - IO Task: 1 (Core 1)
   - Cloud Task: 1 (Core 1)
   - System Task: 1 (Core 0/1)

#### ✅ Low Priority: Code Safety
1. **WDT Feed points:** In extremely long functions (like `publishHomeAssistantDiscovery`), insert explicit `esp_task_wdt_reset()` calls if the function is known to exceed 1 second.

---

### 5. FINAL VERDICT
Crash 4 confirms that Crash 3 was not an isolated incident. The Lumina firmware has "Core 0 Exhaustion." By migrating the high-level application tasks (`CloudTask`, `IOTask`) to Core 1, you will give the ESP32's networking core the breathing room it needs to maintain stability.
