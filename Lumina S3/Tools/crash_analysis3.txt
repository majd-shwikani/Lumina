# Crash Analysis Report - Lumina LED Controller
## Crash ID: 3 (coredump3.txt)
## Date: 2026-04-18

---

### 1. SUMMARY
- **Crash Type:** Task Watchdog Timer (TWDT) Timeout / Abort
- **Core:** 0
- **Crashed Task:** `CloudTask` (TCB: 0x3fcb9b1c)
- **Watchdog Timeout:** 30 Seconds
- **Primary Cause:** Core 0 CPU Starvation. The IDLE task on Core 0 was unable to run for over 30 seconds, triggering the hardware watchdog.

---

### 2. DETAILED ANALYSIS

#### A. The Smoking Gun: Task Watchdog
The crash log explicitly states: `abort() was called at PC 0x420907d0 on core 0`. This PC corresponds to the `task_wdt_isr`. In the ESP32 Arduino framework, the Task Watchdog monitors the IDLE task. If the IDLE task is starved of CPU time (because higher priority tasks are hogging the core), the watchdog triggers a system reset/panic.

#### B. Core 0 Overload
Analysis of the task table shows that Core 0 is significantly overloaded compared to Core 1:
- **Core 0 Tasks:**
  - `Stream_22` (Priority 3) - Firebase Stream (High CPU during SSL/JSON)
  - `CloudTask` (Priority 1) - Firebase Uploads (High CPU during BearSSL/TLS)
  - `IOTask` (Priority 1) - MQTT & Smart Home (Blocking delays during Discovery)
  - `wifi` (Priority 23) - WiFi Driver
  - `SystemTask` (Priority 0) - Automation & Sensors
  - `IDLE0` (Priority 0) - Watchdog resetter
- **Core 1 Tasks:**
  - `LEDTask` (Priority 1)
  - `loopTask` (Priority 1)
  - `IDLE1` (Priority 0)

With four active tasks at Priority 1 or higher on Core 0, the tasks at Priority 0 (`SystemTask` and `IDLE0`) are only allowed to run when all others are yielding.

#### C. Priority Inversion & Deadlock Risk
The stack trace shows a critical conflict:
1. **`SystemTask` (Priority 0)** was in the middle of `updateSensorData()`, holding the I2C semaphore while communicating with the VEML7700 sensor.
2. **`CloudTask` (Priority 1)** also calls `updateSensorData()` at the start of its loop.
3. If `CloudTask` preempts `SystemTask` and then tries to call `updateSensorData()`, it will **block** waiting for the I2C semaphore held by the lower-priority `SystemTask`.
4. While `CloudTask` is blocked, **`IOTask`** (Priority 1) or **`Stream_22`** (Priority 3) can take the CPU. 
5. Because `SystemTask` is at Priority 0, it will **NEVER** run as long as `IOTask` or `Stream_22` have work to do.
6. This creates a state where the I2C semaphore is never released, `CloudTask` stays blocked, and the `IDLE0` task is completely starved.
7. After 30 seconds of this condition, the Watchdog triggers.

#### D. Expensive Operations
- **BearSSL (TLS):** The `CloudTask` was inside `BSSL_SSL_Client::connect`. SSL handshakes are extremely CPU-intensive on the ESP32 and can take several seconds, during which time the task might not yield enough for the IDLE task.
- **MQTT Discovery:** The `IOTask` calls `publishHomeAssistantDiscovery()` which contains multiple `delay(200)` calls, totaling ~3.2 seconds of blocking time at Priority 1.

---

### 3. IMPORTANT RECOMMENDATIONS

#### ✅ High Priority: Fix Task Scheduling & Priorities
1. **Balance Cores:** Move `CloudTask` or `IOTask` to **Core 1**. Currently, Core 0 is doing 90% of the heavy lifting.
   - *Change:* `xTaskCreatePinnedToCore(cloudTask, ..., 1);` // Move to Core 1
2. **Increase `SystemTask` Priority:** Raise `SystemTask` to **Priority 1**. Never put critical system logic at Priority 0 (IDLE level) if it holds resources like I2C semaphores.
3. **Harmonize Sensor Access:** Stop calling `updateSensorData()` from both `SystemTask` and `CloudTask`.
   - *Fix:* Let `SystemTask` update the global `currentLux` every 500ms, and let `CloudTask` simply read the global value for its 2-second telemetry upload.

#### ✅ Medium Priority: Code Optimization
1. **Non-blocking MQTT Discovery:** Replace `delay(200)` in `publishHomeAssistantDiscovery()` with `vTaskDelay(200 / portTICK_PERIOD_MS)`. This allows the IDLE task to run during the delay.
2. **Watchdog Strategy:** Ensure that long-running operations like BearSSL handshakes or large JSON parsing blocks periodically call `vTaskDelay(0)` or `yield()` to allow the scheduler to breathe.

#### ✅ Low Priority: I2C Reliability
1. **I2C Timeout:** Ensure the `Wire` library has a reasonable timeout to prevent a hung sensor from locking the entire system.

---

### 4. CONCLUSION
The crash was not a memory leak or a null pointer, but a **scheduling failure**. The combination of resource contention (I2C) and priority starvation caused Core 0 to "lock up" from the perspective of the Watchdog Timer. Following the recommendation to move tasks to Core 1 and synchronize sensor reads will likely resolve this permanently.
