# ESP32-S3 Crash Analysis Report
**Date:** April 17, 2026
**Crash Cause:** DebugException (0x41) / Memory Corruption during BearSSL Handshake
**Crashed Task:** `IOTask` (Core 0)
**Context:** Concurrent use of Firebase RTDB from MQTT Callback and Sensor Upload Task.

## 1. Executive Summary
The ESP32-S3 experienced a fatal crash while processing an MQTT command that attempted to update Firebase Realtime Database. The crash occurred within the BearSSL library (used by `Firebase-ESP-Client`) during an RSA signature verification process. The root cause is a race condition where the global `fbdoUpload` object was accessed concurrently by two different FreeRTOS tasks (`IOTask` and `CloudTask`).

## 2. Technical Root Cause Analysis

### A. Race Condition on `fbdoUpload`
The codebase uses a single global `FirebaseData` object named `fbdoUpload` for almost all outgoing RTDB operations:
- **CloudTask**: Uploads sensors and stats every 2 seconds.
- **IOTask**: Handles MQTT commands (in `mqttCallback`) and updates device state in Firebase.
- **SystemTask**: Updates timer states.

Both `CloudTask` and `IOTask` are pinned to Core 0 with the same priority (1). Since Firebase operations are blocking (network I/O), the FreeRTOS scheduler can switch tasks while one task is waiting for a network response. If `CloudTask` is mid-operation and `IOTask` starts another operation using the same `fbdoUpload` object, the internal state (including SSL context and TCP buffers) becomes corrupted, leading to the observed crash in BearSSL.

### B. Insufficient Stack Size
- `IOTask` was created with a stack size of **6000 bytes**.
- BearSSL (RSA i31) is extremely stack-intensive. The core dump shows that at the time of the crash, `IOTask` had only **1612 bytes** of stack remaining. 
- Complex SSL handshakes or certificate validations can easily exceed this remaining space, leading to a stack overflow or memory corruption.

### C. SSL Context Corruption
The stack trace shows the crash at `br_i31_decode_mod + 86`. This function is part of the big-integer math used for RSA. The invalid memory access (`0x3fccbf8c`) suggests that the pointer to the modulus or the source data was corrupted by the concurrent task.

The trace clearly shows the `mqttCallback` invoking a synchronous Firebase `setBool` operation using `fbdoUpload` while another task (`Stream_92` or `CloudTask`) was likely active.

## 4. Recommendations

### Immediate Fixes (Required)
1. **Separate FirebaseData Objects**: 
   - Create a dedicated `FirebaseData` object for each task.
   - Example: `fbdoCloud` for `CloudTask` and `fbdoMQTT` for `IOTask`.
   - Never share a `FirebaseData` object across different FreeRTOS tasks.

2. **Increase Stack Sizes**:
   - `IOTask` should be increased to at least **10240 bytes (10KB)** or **12288 bytes (12KB)** to safely handle SSL handshakes.
   - The coredump confirms 6KB is too close to the limit.

### Architectural Improvements
3. **Decouple MQTT from Firebase**:
   - Avoid calling blocking Firebase functions (`setBool`, `setInt`, etc.) directly inside the `mqttCallback`.
   - Instead, set a flag or push a command to a queue that the main loop or a dedicated worker task processes. This keeps the MQTT loop responsive and prevents deep nesting of network calls.

4. **Use Mutex Protection**:
   - If you must use a shared object, wrap all Firebase calls in a `Semaphore` or `Mutex`. However, separate objects are significantly better for performance on the ESP32.

5. **Enable PSRAM for BearSSL**:
   - Since the ESP32-S3 has PSRAM, ensure the Firebase library is configured to use it for large buffers (if supported by the version in use), which reduces pressure on the internal DRAM.

## 5. Conclusion
The crash is a classic concurrency bug. By isolating the Firebase data objects and providing sufficient stack memory, the system stability will be significantly improved, especially when handling simultaneous updates from MQTT and internal sensors.
